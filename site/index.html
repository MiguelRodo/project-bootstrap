Project setup that agents can follow

Set up a project. Keep its GitHub work in order.

Project bootstrap follows one setup procedure for a research or teaching project. Drive holds its description; GitHub holds its code and tasks. There is also a manual hand-off for the ChatGPT Project.

For ongoing work, the github-project-admin skill applies your repository’s rules. The optional projects CLI handles the supported GitHub operations.

From setup to everyday work

Follow the path you need.

Start with the full arrangement, extend an existing GitHub setup, or connect Chat to local execution. Each path uses the same repository contracts and checks the result before calling it done.

1. Drive, GitHub and ChatGPT 2. Add another GitHub Project 3. Set up pj -i

The full arrangement

Connect the project description, tasks and conversation.

Have the project name, year, research or lecturing category, short purpose and any explicitly chosen contacts ready. Decide whether to reuse or create its GitHub repository and Project. The agent will propose a lowercase folder slug and reuse verified resources when resuming an existing setup.

  1. Prepare access and review the proposed setup

    Install the bootstrap skill. Give the chosen agent authenticated access to GitHub, Google Drive and your task system’s Global tasks spreadsheet. The spreadsheet’s Projects tab is the registry connecting the systems; its live headers decide the row format. If the registry is missing, resolve that setup first rather than inventing a second registry.

    For local GitHub access, check gh auth status; the GitHub prerequisites cover sign-in and Project permissions. Connect the Drive and GitHub apps available in your chat and check that it can open the intended resources. Then ask the bootstrap skill for the setup. It inspects existing identities and presents the resources, files and registry row for your approval.

  2. Resolve GitHub, then create the Drive source folder

    The agent first verifies or creates the requested repository and GitHub Project. It then creates only missing folders at the approved Drive path: 

    work/projects/<year>/<research|lecturing>/<project-slug>/
├── README                 native Google Doc
└── references/
    └── llm/

    The native README Doc holds the purpose, supplied contacts, directory description and verified links. Its Details section starts empty; reference material goes into references/llm/ when supplied. This is the canonical source folder. The task system’s projects/work/... mirror is a derived view.

  3. Connect the repository and register the project

    When both GitHub resources are used, install github-project-admin in the repository and run its initializer. The agent adds the bounded project-resources section to the repository README and records required source links in the resolved contract, within the repository’s privacy rules. Private source URLs belong only in authorised private destinations. Review, validate, commit and push the configuration through that repository’s contribution workflow.

    The agent then adds or updates exactly one Global tasks → Projects row with the verified Drive folder and GitHub identities. It preserves unrelated cells, records the change in an existing Change log and reads the row back. GitHub issues and Projects hold current task state; the registry links resources, and GitHub cache tabs remain pull-only.

  4. Create the private ChatGPT Project and check its sources

    This step is manual. Create or open the intended ChatGPT Project. In Sources, add the verified Drive README and references/llm/ folder through the available Drive connection, and make the GitHub repository accessible. Save the supplied Project instructions: they route background questions to Drive and task operations to the repository’s AGENTS.md, including the configured local handoff.

    Connected-source controls depend on your app and workspace. Check the official Projects guide if the controls differ, and leave unavailable source access pending. In a new Project chat, ask it to open the README and retrieve the repository’s AGENTS.md. Confirm both sources, repository access and saved instructions before marking the manual handoff complete.

  5. Verify the arrangement and start using it

    Check the Drive links, repository resources, validated contract and single registry row. Ask for a read of the existing GitHub issues. Confirm any pending Priority mapping before requesting a priority change; broad reorganisation starts with a proposal. If Chat cannot finish an authorised change, use the local queue.

    To resume, ask: “Use $project-bootstrap to finish setting up Foobar and verify the result.” The agent checks the completion conditions and reports any missing access or remaining manual step.

Extend an existing installation

Add another GitHub Project without starting over.

Start in the repository that stores the new Project’s issues. Have its owner and Project number ready. An existing multi-Project setup has Mode | dispatcher in .projects/project.md and one child contract per Project. Rerun the installed initializer:

Existing repository root 
bash .agents/skills/github-project-admin/scripts/init-project.sh

It preserves current routes, discovers the additional Project and asks for its unique Project key and routing label. The new child contract lives under .projects/projects/. The initializer validates the result and offers to commit and push the onboarding files. Review that diff through your repository’s normal workflow, confirm the new Priority mapping and have the agent verify live routing and membership before using the route. The initializer itself changes repository files only.

For Mode | single, rerunning the initializer preserves the current setup and exits. Ask the agent to propose a conversion to a dispatcher: preserve the first Project’s mappings and governance in a child contract, add distinct routes for both Projects, and identify any required live routing-label changes while preserving existing membership and values. Approve the concrete conversion before it applies and verifies it. Keep the existing contract throughout the conversion.

If the new Project belongs to another repository, use the repository installation there. If it also needs Drive and ChatGPT resources, resume the full bootstrap path with the verified GitHub identities. The contract reference defines the routing and validation rules.

Finish Chat work locally

Set up and use pj -i.

A chat that can create issues and comments can hand an authorised change to your local agent when it cannot finish the work itself. It may also mark an existing implementation issue for later work. The handoff is queued until local execution and verification complete.

  1. Install the launcher and prepare its workspace

    Install and authenticate one supported agent, then clone this repository and run its installer. The operator guide covers PATH, backend selection and installation details.

    Terminal, in your chosen parent directory 
    gh repo clone MiguelRodo/project-bootstrap
cd project-bootstrap
bash operator/install.sh
gh auth status
pj --show-default

    Reuse an existing checkout if you have one. Keep managed repository checkouts under ~/planning, or the directory selected by PJ_WORKSPACE. Each needs its AGENTS.md, installed administration skill and validated .projects contracts. Local gh needs access to the declared repositories and Projects.

  2. Enable the handoff and queue a bounded request

    Check that the resolved Project contract includes Chat implementation label | pj:implement-chat; new contracts include it by default. For a dispatcher this belongs in each participating child contract. Existing installations can add it through their normal configuration review. Use the queue-aware Project instructions so the chat follows the configured handoff.

    Ask Chat for the change you want. The skill labels the existing implementation issue, or creates a small temporary handoff, and adds a separate unedited comment beginning PJ implementation authority:. That comment states the bounded goal; repository work also names every target repository. Temporary handoffs are not added to the Project just for being queued. If the chat cannot create the issue or authority comment, it gives a minimal command and result-check handoff instead.

  3. Process the queue and check the result

    Run when ready to execute queued work 
    pj -i

    Use pj -i --repo example/repository to select one exact managed issue repository, or pj -o -i --repo example/repository to exit after the processing turn. pj --implement-issues and pj --implement-chat are aliases for pj -i. Discovery stays within the local contracts.

    Automatic execution requires the issue and the latest applicable unedited authority comment to be authored by the GitHub user authenticated locally. Other authors, edited or missing authority comments, and ambiguous or suspicious requests need local review. The agent rechecks current state, follows the repository’s contribution rules and verifies each result before removing the queue label and closing a completed handoff. Implementation issues follow the repository’s normal completion policy; an open PR or failed check leaves work pending.

pj launches the agent using local authentication; this queue does not run a GitHub Actions bridge. The optional projects binary supplies supported administration commands. The shared queue reference owns the execution rules.

The optional Go CLI

See the plan before anything changes.

The projects command covers the GitHub sequences that benefit from one maintained implementation. It validates the local contract first. Mutation commands show a plan unless you add --apply.

Bound to the repository
Supplied repository names and URLs must agree with the contract.
Small reads
Mutation checks start from the target issue rather than downloading the Project.
Checked afterwards
The command reads the result back before it reports success.

Create an issue and set its starting fields

$ projects issue create \ --title "Add telemetry preflight" \ --priority P1 --class Task --status Todo Plan only. Supply --apply to create the issue on GitHub.

Apply the same checked request

$ projects issue create \ --title "Add telemetry preflight" \ --priority P1 --class Task --status Todo --apply

Update one existing Project item

$ projects project item-edit \ --issue 139 --priority P2 --status "In progress" --apply

One home-level policy

Your agents can read the same standing instructions.

The operator installer treats ~/AGENTS.md as the canonical user guidance. New or installer-owned backend files link to it through the filename each supported agent expects.

A regular file with custom instructions keeps its text; only its managed block is refreshed. An unrelated symlink is left alone.

Codex and Copilot can delegate bounded work to agy after you authorise it for the task or conversation. The primary agent still makes the decisions and verifies the result. Read the permission and migration details.

A few straight answers

What this does — and what it does not.

Does the CLI replace the skill?

No. The skill interprets the request and applies the project’s rules. The CLI handles supported operations that are worth implementing once and testing carefully.

Do I need the CLI?

No. The skill can still use repository scripts or direct GitHub operations. Install the CLI when its commands save work or make a repeated sequence easier to trust.

Does bootstrap create the ChatGPT Project?

Version 1 leaves that step as a checked manual hand-off. The procedure gives you the exact setup and verification steps.

Where do credentials go?

They stay outside the public repositories. The checked-in files contain collaborator-safe configuration and instructions only.
